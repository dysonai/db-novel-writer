# 方法论:以数据库为中心的小说创作

## 一、核心隐喻:把小说当成一款策略 RPG

玩过《博德之门3》的人都知道:游戏世界里每一个 NPC、每一件物品、每一段对话,
都有一张"状态表"——它知道你现在持有哪把剑、对某个人物的好感度多少、某个任务进行到哪一步。
作者写长篇小说时脑子里的"一致性",本质上就是**同一张状态表**。

没有状态表,你只能靠记忆硬撑:
- "上一次黛玉是在哪个房间听见哭声的?" → 凭印象,容易错
- "这颗芯片现在在谁手里?" → 写到第三卷就糊涂了
- "这个伏笔埋了十几章,到底回收了没?" → 靠翻前文,累且漏

`db-novel-writer` 的做法:**用 SQLite 把这张状态表显式地建出来**。
数据库是单一真相源(Single Source of Truth),正文只是它的"渲染层"。

## 二、四感知模型(perceptions 表)

这是本 skill 区别于普通"人物卡"的关键。每个场景里,我们不为角色写一段"内心独白",
而是把角色的**所见所闻所感所想**拆成可查询的原子记录:

| ptype | 含义 | 写作中的用途 |
|-------|------|------------|
| SEE   | 见   | 角色实际看到了什么(客观事实层) |
| HEAR  | 闻   | 听到了什么声音/对话 |
| FEEL  | 感   | 情绪/身体感受 |
| THINK | 想   | 判断/推断(角色自己的逻辑,可能是错的) |
| KNOW  | 已知 | 角色此刻已掌握的事实(信息差的核心) |
| SAY   | 言   | 说出口的话 |
| DO    | 行   | 动作 |

**为什么这样拆?**
因为"前后文不一致"几乎都发生在感知层:
- 同一个角色,Ch3 说"从没见过红色PCB",Ch9 却"一眼认出仿板" → THINK/SEE 冲突
- 读者以为角色知道的事,角色其实不知道 → 靠 KNOW 与"读者信息"对比,制造信息差
- 道具 A 在 Ch5 被销毁,Ch8 又被人拿在手里 → 查 prop_transfers 立刻现形

每条感知可带 `target_type/target_id`(指向具体角色/道具/事件)与 `confidence`(fact/inferred/unknown),
于是"哪条事实是角色推断的、可能错"也变得可审计。

## 三、读者信息差(从 plan-fiction 借来的魂)

那篇公众号文章里的 `plan-fiction` skill 真正值钱的思想,不是"用 Gemini 写",
而是它强调的**内外因果**与**读者/角色信息差**。本 skill 把这一点落进数据库:

- **KNOW(角色已知)** vs **读者已知**:用 `perceptions(ptype=KNOW)` 明确角色此刻掌握什么。
- 写悬疑时,**让角色比读者晚知道关键信息**是张力来源——数据库让这种"刻意的不对称"可控、可复核。
- 写反转时,回头查某角色在关键节点的 KNOW,确保反转不靠"作者临时塞记忆"作弊。

> 文章里的"一次只问一个问题、避开俗套、六种反套路角度"属于**大纲构思阶段**的方法,
> 不在本 skill 范畴(那是 plan-fiction 的事)。本 skill 专注**落笔后的状态一致性**。
> 两者互补:用 plan-fiction 长出大纲,用 db-novel-writer 守住大纲不被写飞。

## 四、标准工作流

```
1. 初始化(一次)
   python init_db.py --db .novel-db/novel.db --seed references/seed-honglou.json

2. 动笔前:查状态(避免写飞)
   python query.py --db .novel-db/novel.db knowledge 林黛玉 --chapter 10
   python query.py --db .novel-db/novel.db prop 幽灵芯片PM-7721
   python query.py --db .novel-db/novel.db foreshadowing --status active

3. 写作(正文照常写,本 skill 不代写)

4. 写完后:抽取场景实体 → 入库
   把该场景的 感知/事件/道具流转 抽成 JSON →
   python capture.py --db .novel-db/novel.db --file scene_ch11_01.json

5. 定期审计
   python audit.py --db .novel-db/novel.db
   python report.py --db .novel-db/novel.db --out .novel-db/report.md
```

## 五、与本项目的接驳

《红楼:硬件鬼才林黛玉》已有并行的"文档型"一致性资产:
- `03-核心道具与线索/伏笔与回收追踪.md`(V01–V22)
- `07-连续性追踪/时间线与状态.md`
- `03-核心道具与线索/关键道具清单.md`
- `02-人物档案/*`

这些文档**继续作为人类可读的权威叙述**保留;本 skill 的数据库是它们的**机器可查询镜像**。
`seed-honglou.json` 即由上述文档策展而来。两者冲突时,以**已发布正文 + 钉死设定**为准,
并用 `audit.py` 把冲突显式暴露,而非静默掩盖。

## 六、边界

- 数据库不写正文、不代写情节——它是"事实账本",不是"创作脑"。
- 凡涉及已发布前8章正文,**一字不改动**(项目铁律);新事实只通过后续章节补叙带入。
- 技术设定(芯片/仿板/功耗调制等)改动须同步 `01-世界观设定` 与 `03-核心道具与线索`,
  并回写 seed 或 capture 增量,保持库与文档一致。
